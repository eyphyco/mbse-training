## bdd は何を表す図か {#bdd-purpose}
items: mu-bdd-purpose
term: ブロック定義図 | ぶろっくていぎず | bdd。ブロックなどの型と、型どうしの関係（持つ・一種である・参照する）を表す図
term: ブロック | ぶろっく | «block»。システムの構造の単位（部品・サブシステム・人・環境など）を定義する型
term: コンポジション | こんぽじしょん | 黒ひし形の線。全体が部分を持ち、全体が無くなれば部分も無くなる関係
term: ステレオタイプ | すてれおたいぷ | «名前» の形で要素に付け、その要素の種類を特定のものに絞る印。プロファイルで定義する

### 一文で

**bdd は型（ブロック）を定義し、型どうしの関係を表す図**。部品表（BOM）と分類表を兼ねる。

`«block»` のように « » で囲んだ印を**ステレオタイプ**と呼ぶ。要素の種類を示す印で、同じ長方形でも印でブロックか値型かが分かる（詳しくは第 11 章）。

| 表すもの | 記号 |
| --- | --- |
| ブロック（型） | `«block»` と書いた長方形 |
| 全体が部分を持つ | **黒ひし形**の線（コンポジション） |
| 一方が他方の一種 | **白三角**の線（汎化） |
| 持たずに指す | 矢じりの線（参照） |
| 値の型 | `«valueType»` の長方形 |

### 何に使うか（利点）

- システムの**分解構造**（何が何でできているか）を 1 枚で示す
- 部品の**種類**（型）を定義し、同じ型を何か所でも使えるようにする
- 値の型・単位・制約式を定義して、ibd・par から使う**部品箱**にする

### bdd と ibd の役割分担

ここが一番混ざる。**bdd は「何があるか」、ibd は「どうつながっているか」**。

| | bdd | ibd |
| --- | --- | --- |
| 描くもの | 型と、型どうしの関係 | 1 つのブロックの**中身** |
| 線の意味 | 持つ・一種・参照 | 部品どうしの**接続** |
| 例 | 車は車輪を 4 つ持つ | 前輪と車軸がこうつながる |

「部品と部品がつながっている」は **bdd では描けない**（ibd の仕事、第 2 章）。

## 定義と使用 {#bdd-def-usage}
items: mu-def-usage
figures: bdd-structure
term: 定義と使用 | ていぎとしよう | 型を定めること（定義）と、その型をある場所で使うこと（使用）を分ける考え方
term: パート | ぱーと | パートプロパティ。ブロックで型付けされた、全体が持つ部分。`名前 : 型` で書く

### ここが最重要

SysML は**定義（definition）と使用（usage）**をはっきり分ける。

| | 定義 | 使用 |
| --- | --- | --- |
| 何か | 型そのもの | ある場所で、その型を使ったもの |
| 例 | `Wheel` というブロック | 車の中の `frontLeft : Wheel` |
| 何個 | 1 つ | 何か所でも作れる |
| bdd では | 箱 | 区画の行、または線の端の名前 |

`Wheel` を 1 回**定義**すれば、`frontLeft : Wheel`、`frontRight : Wheel`、`spare : Wheel` のように何か所でも**使える**。
使用は `名前 : 型` で書く。**コロンの左が使用の名前、右が定義（型）**。

### 図で読む

下の図で `Vehicle` の `parts` 区画にある `wheels : Wheel [4]` は「Vehicle の中で Wheel という型を wheels という名前で 4 つ使う」という意味。
黒ひし形の線と `parts` 区画の行は、**同じことの 2 通りの書き方**（線の端の `wheels` と `4` が区画の行と一致している）。

### 試験での問われ方

- 「`engine : Engine` の `Engine` は何か」→ 型（ブロック）。`engine` はパートの名前
- 「同じブロックを 2 か所で使えるか」→ 使える。それが定義と使用を分ける理由

## ブロックの区画 {#bdd-features}
items: mu-block-features
figures: bdd-structure
term: 区画 | くかく | コンパートメント。ブロックの箱の中を横線で区切った部分。parts / values など見出しで種類を示す
term: 値属性 | ちぞくせい | value property。値型で型付けされた属性（質量・速度など）。values 区画に書く
term: 参照 | さんしょう | reference property。持たずに指すだけの属性。references 区画に書く
term: 操作 | そうさ | operation。ブロックが受け付ける呼び出し。operations 区画に書く
term: 多重度 | たじゅうど | 何個あるかの範囲。`1` `0..1` `*` `1..*` `2..4` のように書く

### 区画の種類

ブロックの箱は、名前の下を**横線で区画に分ける**。区画の見出し（英語のまま）で中身の種類が分かる。

| 区画 | 何を書くか | 型 | 例 |
| --- | --- | --- | --- |
| `parts` | 持っている部品 | ブロック | `engine : Engine` |
| `references` | 持たずに指す相手 | ブロック | `driver : Driver` |
| `values` | 量・性質 | 値型 | `mass : Mass` |
| `constraints` | 制約式 | — | `{mass <= 1500}` |
| `operations` | 呼び出せる操作 | — | `accelerate(rate : Real)` |
| `flowPorts` / `ports` | 出入口 | — | 第 2 章で扱う |

### 見分けの要点

- **parts と references の違い**: parts は**持ち物**（全体が消えれば消える）、references は**指すだけ**（相手は独立して存在する）
- **parts と values の違い**: 型が**ブロック**なら parts か references、**値型**なら values
- 区画は**省略できる**。描いていない区画は「無い」ではなく「この図では見せていない」（章 0 の「モデルと図は別物」）

### 行の書き方

```
名前 : 型 [多重度] = 既定値
mass : Mass = 1500
wheels : Wheel [4]
```

`[ ]` が無ければ多重度は **1**。

## 値型と単位 {#bdd-valuetype}
items: mu-valuetype
figures: bdd-valuetypes
term: 値型 | ちがた | «valueType»。量や性質の型。実体を区別せず、値だけが意味を持つ。単位と次元を持てる
term: 単位 | たんい | unit。値型の値をどの尺度で測るか（kg・m/s など）
term: 列挙 | れっきょ | «enumeration»。取りうる値を名前で並べた値型

### ブロックとの違い

| | ブロック | 値型 |
| --- | --- | --- |
| 印 | `«block»` | `«valueType»` |
| 何を表す | 部品・もの | 量・性質 |
| 実体の区別 | **する**（2 台の同じ車は別物） | **しない**（1500 kg はどこでも 1500 kg） |
| 使われる区画 | parts / references | **values** |
| 部品や出入口を | 持てる | **持たない** |

**値は「どれか」を区別しない**。1500 kg という値が 2 つあっても同じもの。だから値型は部品も出入口も持たない。

### 単位と次元

値型は**単位**（unit、kg）と**次元**（dimension、質量）を持てる。図では名前の下に `{unit = kg}` のように出る。

`mass : Real` と書くより `mass : Mass`（Mass は単位 kg を持つ値型）と書く方が、**単位の取り違えをモデルが防げる**。
試験で「値属性の単位をどこで定めるか」と問われたら、**値型**で定める。

### 列挙

取りうる値が決まっているものは `«enumeration»` で並べる（`park / reverse / neutral / drive`）。列挙も値型の一種。

### 基本型

`Real` `Integer` `Boolean` `String` は SysML が最初から持つ基本の値型。そのまま values 区画の型に使える。

## 関連・コンポジション・参照 {#bdd-association}
items: mu-association
figures: bdd-structure, bdd-diamonds
term: 関連 | かんれん | association。2 つのブロックの間の構造上の関係を表す実線
term: 共有集約 | きょうゆうしゅうやく | 白ひし形の線。部分を共有してよい関係。Model User の範囲外だが黒との区別に要る

### 線の種類

| 線 | 名前 | 意味 | 区画で書くと |
| --- | --- | --- | --- |
| 黒ひし形 ◆— | コンポジション | **持ち物**。全体が消えれば部分も消える | parts |
| 白ひし形 ◇— | 共有集約 | 共有してよい部分 | references |
| 矢じりだけ —> | 参照（関連） | 指すだけ。矢じりの向きに辿れる | references |
| 飾りなし — | 関連 | 構造上の関係がある | — |

### ここが最重要: ひし形は**全体の側**

```
Vehicle ◆———— Wheel
 全体          部分
```

**ひし形は持つ側（全体）の端**に付く。部分の側ではない。
向きを取り違えると「車輪が車を持つ」意味になる。迷ったら **parts 区画を見る**: `Vehicle` の parts に `wheels : Wheel` があるなら、ひし形は Vehicle の側。

### 黒と白の違い

- **黒（コンポジション）**: 部分は**同時に 1 つの全体にしか属さない**。全体が消えると部分も消える。エンジンは 1 台の車にしか載らない
- **白（共有集約）**: 部分を**共有してよい**。全体が消えても部分は残る。車両は車隊に属するが、車隊が解散しても車両は残る

> 共有集約は Model User の範囲外（syllabus に明記）。それでも**黒との取り違え**は誤り指摘の定番なので、見分けられるようにしておく。

### 試験での問われ方

- 「Vehicle が消えたら Wheel はどうなるか」→ 黒なら消える、白・参照なら残る
- 「parts 区画にあるのに線が白ひし形」→ 食い違い（誤り）

## 多重度 {#bdd-multiplicity}
items: mu-multiplicity
figures: bdd-structure, bdd-diamonds
term: ロール名 | ろーるめい | 関連の端に書く名前。その端の相手が、反対側からどう呼ばれるか

### 書き方

| 書き方 | 意味 |
| --- | --- |
| `1` | ちょうど 1 つ（書かなければこれ） |
| `0..1` | 無いか、1 つ |
| `*` | 0 個以上（`0..*` と同じ） |
| `1..*` | 1 つ以上 |
| `4` | ちょうど 4 つ |
| `2..4` | 2〜4 つ |

### ここが最重要: 多重度は**相手の端**に書く

```
Vehicle ◆———————— Wheel
                wheels
                   4
```

「車 1 台が車輪をいくつ持つか」の `4` は、**Wheel の側の端**に書く。
読み方は「**Vehicle 1 つあたり、Wheel が 4 つ**」。数えられる側（部分）の端に置く、と覚える。

ロール名（`wheels`）も同じ端に書く。ロール名は「Vehicle から見たときの Wheel の呼び名」で、parts 区画の `wheels : Wheel [4]` の `wheels` と同じもの。

### コンポジションの全体側

黒ひし形の**全体の側**の多重度は、**`1` か `0..1` にしかならない**。部分は同時に 2 つ以上の全体に属せないから。
全体の側に `4` が書いてあったら、それは**書く端を取り違えた**誤り。

## 汎化（特化） {#bdd-generalization}
items: mu-specialization
figures: bdd-generalization
term: 汎化 | はんか | generalization。白三角の線。特化した型が、一般の型の性質をすべて受け継ぐ関係
term: 抽象ブロック | ちゅうしょうぶろっく | 名前が斜体のブロック。それ自体の実体は作らず、特化の元として使う

### 読み方

```
ElectricVehicle ———▷ Vehicle
   特化した側          一般の側
```

**白三角は一般の側**に付く。「ElectricVehicle **は** Vehicle **の一種**」と読む。

| | 中身 |
| --- | --- |
| 受け継ぐもの | 一般の側の**すべての**属性・区画の行・関係 |
| 足せるもの | 特化した側だけの属性（`batteryCapacity`） |
| 変えられるもの | 受け継いだ属性を**再定義**して絞る（`{redefines mass}`） |

### 抽象ブロック

名前が**斜体**のブロックは抽象。それ自体の実体は作らず、特化の元にだけ使う。「車両」という実体は無く、実在するのは電気自動車か内燃機関車のどちらか、という表し方。

### コンポジションとの取り違え

| 問い | 線 |
| --- | --- |
| A は B **の一種**か（is-a） | 汎化（白三角） |
| A は B **を持つ**か（has-a） | コンポジション（黒ひし形） |

「エンジンは車の一種」ではないので、車とエンジンの間は汎化ではない。**「〜は〜の一種」と声に出して自然か**で判定する。

### 同じ種類どうしだけ

汎化は**ブロックとブロック**、**値型と値型**の間に引く。ブロックが値型を特化することはできない。

## 構造をモデルでどう捉えるか {#bdd-capture}
items: mbf-struct-capture
term: 分解 | ぶんかい | システムを部分に分けること。bdd ではコンポジションの木として表す

### 構造を捉える 3 つの問い

Model Builder は「この状況をどうモデル化するか」を問う。構造は次の 3 つの問いで捉える。

| 問い | 道具 | 図 |
| --- | --- | --- |
| 何で**できているか** | コンポジション（分解の木） | bdd |
| 何の**一種か** | 汎化（分類の木） | bdd |
| どう**つながっているか** | パートどうしの接続 | ibd |

### 判断の分かれ目

| 状況 | 選ぶもの | 理由 |
| --- | --- | --- |
| 全体が無くなれば部分も無くなる | コンポジション | 持ち物 |
| 相手は独立して存在し、指すだけ | 参照（矢じり） | 持っていない |
| 量・性質（質量・温度） | 値属性 + 値型 | 実体を区別しない |
| 種類の違いを表したい | 汎化 | is-a |
| 同じ型を何か所でも使う | 1 つのブロック + 複数のパート | 定義と使用 |

### よくある誤り

- **量をブロックにする**: `Mass` を `«block»` にしない。値型にする
- **使用ごとにブロックを作る**: 前輪と後輪で `FrontWheel` `RearWheel` を作らず、`Wheel` 1 つを 2 か所で使う（形が違うなら汎化で分ける）
- **接続を bdd に描こうとする**: つながりは ibd

## bdd を作る {#bdd-build}
items: mbf-build-bdd
figures: bdd-structure

### 手順

1. **ヘッダを決める**: `bdd [package] 構造の置き場 [図の名前]`。分解を見せるなら `[block] 最上位のブロック` でもよい
2. **最上位のブロック**（システム）を置く
3. **分解**: 部分のブロックを置き、黒ひし形で全体から引く。**部分の側に多重度とロール名**
4. **分類**: 種類の違いがあれば汎化（白三角は一般の側）
5. **値**: 量を値型で定義し、values 区画に `名前 : 値型`
6. **区画と線を揃える**: parts 区画に書いたなら、線の端のロール名・多重度と一致させる

### 確かめる観点（誤り指摘で問われる所）

| 観点 | 正しい形 |
| --- | --- |
| ひし形の位置 | 全体の側 |
| ひし形の塗り | parts 区画にあるなら黒 |
| 多重度・ロール名の位置 | 部分の側 |
| 全体側の多重度 | 1 か 0..1 |
| values の型 | 値型（ブロックではない） |
| parts の型 | ブロック（値型ではない） |
| 汎化 | 白三角は一般の側。同じ種類どうし |
| ヘッダ | `bdd`、型は package / model / modelLibrary / block / constraintBlock |
