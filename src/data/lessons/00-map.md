## MBSE とは何か — なぜ文書ではなくモデルか {#map-mbse}
items: mbf-what-is-model
term: MBSE | えむびーえすいー | Model-Based Systems Engineering。システムの要求・構造・振る舞いを、文書ではなくモデルを正本にして設計する進め方
term: モデル | もでる | 対象のシステムを、目的に必要な側面だけ取り出して表したもの。SysML では要素と関係の集まり
term: SysML | しすえむえる | システムズエンジニアリングのためのモデリング言語。UML を土台に拡張したもの。OCSMP の対象は v1.2

### 文書中心の何が困るか

従来の設計は**文書が正本**だった。要求仕様書・設計書・試験仕様書が別々にあり、同じ事実が何か所にも書かれる。

| 困りごと | 起きること |
| --- | --- |
| 同じ事実が複数の文書にある | 1 か所直すと他が古くなる。どれが正しいか分からなくなる |
| 関係が文章の中に埋もれる | 「この要求を満たす部品はどれか」を答えるのに全文を読む |
| 整合の確認が人手 | 変更の影響範囲を見落とす |

### モデルを正本にする

**MBSE**（Model-Based Systems Engineering）は、要求・構造・振る舞い・解析を**1 つのモデル**に入れ、そこから必要な見え方（図・表・文書）を取り出す。

- 事実は**モデルに 1 回だけ**書く。図はモデルの一部を**切り取った見え方**
- 要素どうしの**関係**（満たす・割り当てる・検証する）をモデルが持つので、辿れる
- 矛盾をツールで検出できる

**モデル**とは、対象を目的に必要な側面だけ取り出して表したもの。**全部を写す必要は無い**。何を表すかは目的（何を決めたいか・何を確かめたいか）で決まる。

### SysML の位置

**SysML** は MBSE のための標準のモデリング言語。ソフトウェア向けの UML を土台に、システム（機械・電気・人・ソフトの組み合わせ）向けに拡張したもの。

> **OCSMP が対象にするのは SysML v1.2**。v1.3 以降や v2 の資料には、試験に出ない記法（フル／プロキシポート、テキスト記法など）が混ざっている。この教材は v1.2 だけを扱う。

## モデルと図は別物 {#map-model-diagram}
items: mbf-model-vs-diagram
term: 図 | ず | モデルの一部を切り取って描いたもの。図を消してもモデルの要素は消えない

### ここが最重要

**図はモデルではない。モデルの見え方**だ。

| | モデル | 図 |
| --- | --- | --- |
| 何か | 要素と関係の集まり（正本） | モデルの一部を描いたもの |
| 同じ要素 | 1 つしか無い | **何枚の図にも**出せる |
| 図から消すと | — | 図から消えるだけ。**モデルには残る** |
| 全部を描くか | — | 描かない。図の目的に要るものだけ描く |

このため、**図に描かれていないことは「無い」とは限らない**。ある図に属性が書いていなくても、モデルの要素は属性を持っているかもしれない（図で隠しているだけ）。

試験では「図から要素を削除した。モデルはどうなるか」「ある要素が 2 枚の図に出ている。それは何個の要素か」の形で問われる。答えは「モデルには残る」「1 個」。

## 図 9 種の地図 {#map-diagrams}
items: mu-header
term: 図枠 | ずわく | 図を囲む長方形。左上の札（ヘッダ）に図の種類と対象を書く
term: ヘッダ | へっだ | 図枠の左上の札。`種類の略号 [対象の型] 対象の名前 [図の名前]` の形
term: ユースケース | ゆーすけーす | アクターに価値をもたらす、システムの使われ方 1 つ分。楕円で描く
term: 振る舞い | ふるまい | システムが時間とともに何をするか。SysML ではアクティビティ・状態機械・相互作用の 3 つで表す

### 9 種と、いつ使うか

SysML の図は **9 種**。名前と略号は**そのまま覚える**（ヘッダに略号で出る）。

| 分類 | 図 | 略号 | 何を表すか | 章 |
| --- | --- | --- | --- | --- |
| 要求 | 要求図 | `req` | 要求と、要求を満たす・検証する要素の関係 | 5 |
| 構造 | ブロック定義図 | `bdd` | **型**（ブロック）とその間の関係 | 1 |
| 構造 | 内部ブロック図 | `ibd` | ブロックの**中身**（パートのつながり方） | 2 |
| 構造 | パラメトリック図 | `par` | 値の間の**制約式**のつながり | 3 |
| 構造 | パッケージ図 | `pkg` | モデルの**整理**（フォルダ分け） | 4 |
| 振る舞い | ユースケース図 | `uc` | 外から見た**使われ方** | 6 |
| 振る舞い | アクティビティ図 | `act` | 処理と物の**流れ** | 7 |
| 振る舞い | 状態機械図 | `stm` | イベントで変わる**状態** | 8 |
| 振る舞い | シーケンス図 | `sd` | 部品間の**やりとりの順序** | 9 |

> **UML から来た人へ**: bdd はクラス図、ibd は合成構造図が元。**要求図とパラメトリック図は SysML で足された図**。UML のクラス図・オブジェクト図・コミュニケーション図などは SysML には無い。

### 図枠とヘッダ

本番の図には**必ず図枠**があり、左上の札（ヘッダ）にこう書かれる。

```
bdd [package] VehicleStructure [Vehicle Decomposition]
 ①      ②           ③                    ④
```

| | 中身 | 例 |
| --- | --- | --- |
| ① | 図の種類の略号 | `bdd` |
| ② | 図が表すモデル要素の**型** | `package` / `block` / `activity` … |
| ③ | その要素の**名前** | `VehicleStructure` |
| ④ | 図の名前（省略できる） | `Vehicle Decomposition` |

図の種類ごとに、②に来られる型が決まっている。

| 図 | ②に来る型 |
| --- | --- |
| `bdd` | package / model / modelLibrary / block / constraintBlock |
| `ibd` | block |
| `par` | block / constraintBlock |
| `pkg` | package / model / modelLibrary / profile / view |
| `req` | package / requirement |
| `uc` | package |
| `act` | activity |
| `stm` | stateMachine |
| `sd` | interaction |

**ヘッダは試験で必ず読む**。「この図は何についての図か」を問う問題は、ヘッダの②と③を見れば解ける。

## 試験の構造 {#map-exam}
items:

### 級と順番

OCSMP は積み上げ式で、**Model User → Model Builder – Fundamental** の順に取る（MBF は MU の合格が前提）。

| | Model User | Model Builder – Fundamental |
| --- | --- | --- |
| 問うこと | 図を**読んで**意味を答える | 基本的なモデルを**作れる**か |
| 問題数 | 90 問 | 90 問 |
| 時間（日本語） | 120 分 | 135 分 |
| 合格 | 56 / 90（62%） | 60 / 90（67%） |
| 形式 | 多肢選択 | 多肢選択 |

### 図を描かない試験で「作る」を問う形

MBF も**多肢選択**で、図を描かせない。問われるのは次の形。

- 「この状況をモデル化するなら、どの構成が正しいか」（選択肢が図）
- 「この図のどこが誤りか」
- 「この図から言えることはどれか」

どれも、**自分で組んだことが無いと選べない**。この教材が誤り指摘（spot_error）を多く置いているのはそのため。

## 前提にする言葉 {#map-oo}
items:
term: 型と実体 | かたとじったい | 型は「どういうものか」の定義、実体はその定義に従って作られた個々のもの
term: 特化 | とっか | 一般的な型を元に、性質を足したり絞ったりした型を作ること。汎化の逆向き

この教材が前提にするのは、オブジェクト指向の**基本語 3 つだけ**。これ以上は前提にしない。

| 語 | 意味 | 例 |
| --- | --- | --- |
| **型と実体** | 型は定義、実体はそれに従う個々のもの | 「車」という型と、あなたの車・隣の車という実体 |
| **特化（継承）** | 一般の型を元に、性質を足した型を作る | 「電気自動車」は「車」を特化した型。車の性質はすべて持つ |
| **合成** | 全体が部分を持つ。全体が無くなれば部分も無くなる | 車は車輪を 4 つ持つ |

SysML ではこの「型」を**ブロック**と呼び、「型を使う場所」を**パート**と呼ぶ（第 1 章）。
詰まったときは、まず「いま見ているのは型か、型を使っている場所か」を問い直すと、たいてい解ける。

## この教材の歩き方 {#map-howto}
items:

### 1 日の流れ

1. **ホームの「今日やる分」を片付ける**。期限が来た項目の問題だけが出る
2. 余裕があれば、新しい項目の**教材を読み、Lv1〜3 を解く**
3. 間違えた項目は**定着度が 0 に戻り、明日また出る**

### 問題の段

| Lv | 型 | 問うこと |
| --- | --- | --- |
| 1 | 図を読む | その記法が**読めるか** |
| 2 | 誤りを見つける | **近い記法と区別できるか** |
| 3 | 構成を選ぶ | **使い所を選べるか** |

### 図は白黒

この教材の図は本番と同じく**白黒**で描く。色で読む癖を付けると、本番の図が読めない。
黒ひし形と白ひし形の違いは**塗りつぶしているか・中抜きか**で読む。

### 今の範囲

図のレンダラは**ブロック定義図（bdd）**から作っている。問題が揃っているのは第 1 章。
ほかの章の教材は全部読めるが、図を使う問題はレンダラが入った順に増える。
