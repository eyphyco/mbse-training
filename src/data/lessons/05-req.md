## 要求という概念 {#req-concept}
items: mu-req-concept
term: 要求 | ようきゅう | «requirement»。システムが満たすべき能力・条件。id と text を持つモデル要素
term: テストケース | てすとけーす | «testCase»。要求が満たされたかを確かめる手順（振る舞い）

### 一文で

**要求は、id と text を持つモデル要素**。文書の 1 行ではなく、他の要素と**関係で結べる**のが要点。

```
«requirement»
MaxSpeed
─────────────
id = "R-1.2"
text = "車両は最高速度 180 km/h を出せること"
```

| 持つもの | 中身 |
| --- | --- |
| 名前 | `MaxSpeed` |
| `id` | 要求番号 |
| `text` | 要求の文 |

### 要求は振る舞いを持たない

要求は**何を満たすか**を言うだけで、**どう満たすか**は言わない。どう満たすかは設計要素（ブロックなど）の仕事で、要求とは「満たす」関係で結ぶ（次の次の節）。

## 要求図は何を表す図か {#req-purpose}
items: mu-req-purpose
term: 要求図 | ようきゅうず | req。要求どうしの関係と、要求と他の要素（満たす・検証する）の関係を表す図

### 一文で

**req は要求の木と、要求を満たす・検証する要素とのつながりを表す図**。

### 利点

- 要求から設計・試験まで**辿れる**（トレーサビリティ）
- 満たされていない要求・試験の無い要求がモデルから見つかる
- 要求を変えたとき、影響する設計と試験が分かる

## 要求の関係 6 種 {#req-relations}
items: mu-req-relations
term: 包含（要求） | ほうがん | 要求を部分要求に分ける関係。親の側に ⊕ の付いた線で描く
term: satisfy | さてぃすふぁい | «satisfy»。設計要素が要求を満たす。矢印は設計 → 要求
term: verify | べりふぁい | «verify»。テストケースが要求を検証する。矢印はテストケース → 要求
term: deriveReqt | でらいぶりくわいあめんと | «deriveReqt»。ある要求から別の要求を導いた。矢印は導いた要求 → 元の要求
term: refine | りふぁいん | «refine»。要求をより詳しく言い換えた（ユースケース・アクティビティなどで）
term: trace | とれーす | «trace»。関係はあるが、ほかのどれにも当たらない弱い関係

### ここが最重要: 名前と向き

**矢印はすべて「〜する側」から「〜される要求」へ向く**。要求が矢印の先に来る、と覚える。

| 関係 | 元（矢印の根元） | 先（矢じり） | 読み方 |
| --- | --- | --- | --- |
| 包含 ⊕ | 親要求（⊕の側） | 子要求 | 親は子でできている |
| `«deriveReqt»` | **導いた**要求 | 元の要求 | 元の要求から導いた |
| `«satisfy»` | **設計要素**（ブロック等） | 要求 | 設計が要求を満たす |
| `«verify»` | **テストケース** | 要求 | 試験が要求を確かめる |
| `«refine»` | 詳しくした要素 | 要求 | 要求を詳しく言い換えた |
| `«trace»` | 何でも | 何でも | 関係がある（弱い） |
| `«copy»` | 写し | 元の要求 | 同じ文を再利用（読み取り専用） |

### 取り違えやすい組

| 組 | 見分け方 |
| --- | --- |
| **deriveReqt と包含** | 包含は**分解**（子を全部満たせば親を満たす）。deriveReqt は**導出**（分析して新しい要求を作った） |
| **deriveReqt と refine** | 新しい条件を**足した**なら deriveReqt。同じことを**詳しく言った**だけなら refine |
| **satisfy と verify** | 満たすのは設計、確かめるのはテストケース |
| **satisfy と allocate** | satisfy は要求に**応える**。allocate は機能を構造に**担当させる**（第 10 章） |

> v1.2 の図に出る綴りは **`«deriveReqt»`**。`«derive»` ではない。

### 表し方

関係は線で描くほか、**吹き出し（コールアウト）**や**区画**でも書ける。

```
«requirement» MaxSpeed
satisfiedBy  «block» Powertrain
verifiedBy   «testCase» SpeedTest
```

`satisfiedBy` / `verifiedBy` / `derivedFrom` / `derived` / `refinedBy` / `tracedFrom` などの名前で出る。どの線と同じ意味かを読み替えられるようにする。

## 要求をモデルでどう捉えるか {#req-capture}
items: mbf-req-capture
term: 根拠 | こんきょ | «rationale»。判断の理由を書き添えるコメント

### 捉え方

| 問い | 道具 |
| --- | --- |
| 要求の分解 | 包含（⊕） |
| 分析から生まれた要求 | `«deriveReqt»` |
| どの設計が応えるか | `«satisfy»` |
| どう確かめるか | `«testCase»` + `«verify»` |
| なぜそう決めたか | `«rationale»` の書き添え |

### 判断の分かれ目

- **1 つの要求に 1 つのこと**。「〜かつ〜」は分ける（検証できる単位にする）
- 文が曖昧なら、使われ方や処理の流れの図で `«refine»` して詳しくする（第 6・7 章）
- 要求を満たす設計は**ブロックかその部品**。要求どうしを `«satisfy»` で結ばない

## 要求図を作る {#req-build}
items: mbf-build-req

### 手順

1. **ヘッダ**: `req [package] 要求の置き場 [図の名前]`（1 つの要求の周りを描くなら `[requirement]`）
2. 最上位の要求を置き、**包含**で分解する（⊕ は親の側）
3. 分析から導いた要求を `«deriveReqt»` でつなぐ（**導いた側から元へ**）
4. 図の目的に応じて、設計要素・テストケースを置く

### 確かめる観点

| 観点 | 正しい形 |
| --- | --- |
| 要求どうし | 包含か deriveReqt（satisfy ではない） |
| 矢印の先 | 要求 |
| verify の元 | テストケース |
| satisfy の元 | 設計要素 |

## 要求を他の要素に結ぶ {#req-to-elements}
items: mbf-req-to-elements

### 結び方の表

| やりたいこと | 関係 | 元 → 先 |
| --- | --- | --- |
| ブロックが要求に応える | `«satisfy»` | ブロック → 要求 |
| 試験で確かめる | `«verify»` | テストケース → 要求 |
| ユースケースで詳しく言う | `«refine»` | ユースケース → 要求 |
| 関係を残したいが種類が決まらない | `«trace»` | — |

### よくある誤り

- `«verify»` の**向きが逆**（要求 → テストケース）
- 要求どうしを `«satisfy»` でつなぐ（要求どうしは包含か deriveReqt）
- 要求からブロックへ矢印を引く（要求は常に**先**）

## 要求を表と行列で表す {#req-table}
items: mbf-req-table
term: 要求表 | ようきゅうひょう | 要求の id・名前・text・関係を行として並べた表。図と同じモデルの別の見え方

### 図以外の見え方

要求は数が多いので、**表と行列**で見ることが多い。これも同じモデルの見え方（章 0）。

| 形 | 何を並べるか | 向いている所 |
| --- | --- | --- |
| 要求表 | 行 = 要求。列 = id / name / text / satisfiedBy … | 一覧・抜け漏れの確認 |
| 行列 | 行 = 要求、列 = 設計要素。交点に関係 | 満たされていない要求を探す |

### 読み方

- 行列で**空の行**がある要求 → まだ何も満たしていない
- 表の `verifiedBy` が空 → 試験がまだ無い

表で関係を足しても、**図と同じモデルに入る**。表と図は食い違わない。
